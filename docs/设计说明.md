# SightClean · 设计说明

> 本文讲**为什么这么设计**，功能怎么用见 [README](../README.md)，验收数据见 [验收记录](验收记录.md)。
> 最后更新：2026-11-15

---

## 一、定位

**一个带用途标注的资源管理器。**

这句话决定了后面所有取舍。它不是"一键优化大师"，而是：

- 列出来 → 写清它是什么 → 你决定

所以有三条不肯让步的规矩：

1. **不主动扫描**：你点哪个目录它才读哪个目录
2. **不替你决定**：默认一个都不勾
3. **不说黑话**：每句话都要能让非技术人员看懂

---

## 二、分层

```
┌─────────────────────────────────────────────┐
│  ui/        界面层                            │
│  main_window（控制器）、*_view（表格）、dialogs │
├─────────────────────────────────────────────┤
│  core/      业务层                            │
│  knowledge（判定）、delete（执行）、ai_client   │
├─────────────────────────────────────────────┤
│  resources/ 数据层                            │
│  规则 JSON、默认配置                           │
└─────────────────────────────────────────────┘
         app_paths.py  贯穿所有层的路径解析
```

**为什么不做 MVC 三层拆到底**

`main_window.py` 有 90 KB，承担了模块切换、工具栏、事件分发。看着臃肿，但它只是**容器**——真正的业务逻辑都在 `core/`，界面层基本是"取数据 → 填表格 → 收信号"。

把它拆成四个 Controller 收益很小，代价是每个模块都要重新理解一遍信号流。需求是"三个模块复用一个容器"，那么容器就该是整体。

新模块用 `page_base.py` 的 `ModulePage` 基类承载，文件页保持原样不动。

## 三、关键决策

### 3.1 判定靠规则，不靠启发式

**决策**：`core/knowledge.py` 只做字符串匹配，**代码里禁止 `os.walk` 参与风险计算**。

**为什么**：一旦判定逻辑开始"看文件大小猜""看修改时间猜"，就变成了黑盒。用户问"你为什么说这是垃圾"，答案只能是"我们的算法觉得是"——这跟这个软件的定位冲突。

87 条规则分成三层，从具体到宽泛：

| 层 | 依据 | 特点 |
|---|---|---|
| 1 | 路径特征 | 最准，几乎不会误判 |
| 2 | 文件名 / 扩展名 | 会误判（`.log` 可能是日志也可能是数据） |
| 3 | 兜底 | 明确说"未收录" |

**匹配顺序**：user 规则整体优先 → layer 1→2→3 → 同层按数组顺序。

**风险用四档而不是三档**：多一个 `unlisted`（未收录），显示成灰色而不是黄色。黄色会让人以为"大概是垃圾"，灰色才准确表达"我不知道"。

### 3.2 长路径统一走前缀转换

**决策**：所有文件系统调用走 `app_paths.to_long()`，显示走 `to_human()`。

```python
def to_long(path) -> str:
    # 本地路径 → \\?\C:\...
    # 网络路径 → \\?\UNC\server\share
```

**为什么必须转换**：Windows API 有个历史遗留的 MAX_PATH = 260 限制。不加前缀时：
- 深度超过 260 的目录列不出来
- 删除会失败
- 但 `os.path.exists()` 可能返回 True（它内部有时会自动加前缀）

这种"部分能用部分不能用"最坑，所以统一在入口转换。

**注意**：`send2trash` 不支持长路径格式，入回收站前要把前缀去掉，用普通路径传。

### 3.3 异步：先画窗口，再做重活

**决策**：`main.py` 里先 `window.show()`，加载逻辑放进 `QTimer.singleShot(0, ...)`。

**为什么**：用户对启动时间的感知是"窗口什么时候出现"，不是"数据什么时候齐"。先 show 再加载，实测窗口 512 ms 出来，首屏 559 ms 就绪。

**线程模型**：

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 大小计算 | `QThreadPool` + `QRunnable` | 任务多、生命周期短 |
| 目录枚举 | 同上 | 要能中途取消 |
| AI 请求 | 串行队列 | 并发会被限流 |
| 注册表操作 | 同步 | 很快，异步反而是负担 |

**取消机制**：`generation` 计数 + `threading.Event`。

```python
self._generation += 1          # 切目录时递增
# worker 里带 generation，回来时对不上就丢弃
if task.generation != self._generation:
    return
```

为什么用计数器而不是取消标志？因为**已经发出去的请求收不回来**，只能丢弃结果。

### 3.4 删除失败要说清真实原因

**决策**：删除失败后**回头查一遍状态**，而不是直接翻译异常码。

**为什么**：Windows 的异常码有歧义。

| 码 | 可能含义 |
|---|---|
| `winerror 5` | 下面有子键 / 真的没权限 |
| `winerror 2` | 真不存在 / 没权限被伪装成不存在 |
| `winerror 32` | 文件被占用 |

同一个码两种含义，直接翻译必然错一半。所以：

```python
def _diagnose(hive, sub, exc):
    # 先看它现在什么样：还在吗？能读吗？几个子键？
    ...
```

文件删除同理——用 `psutil` 枚举进程，看哪个的 exe 落在目标目录下，报出具体名字：

```
这个目录里的程序正在运行：chrome.exe。先关掉它们再试
```

**已知局限**：只能查"进程的 exe 在目录下"，查不到"进程打开着目录里的某个文件"。后者需要查句柄表，复杂度高一个量级。所以策略是**能查就报名字，查不到就说"被占用"**，不编造。

### 3.5 注册表：键级和值级分开

**决策**：`registry.py` 管键，`regvalue.py` 管值。

**为什么**：这是两个不同的 Win32 操作。

```python
winreg.DeleteKey(hive, sub)          # 删键（必须没有子键）
winreg.DeleteKeyEx(hive, sub, ...)   # 删键（可删整个子树）
winreg.DeleteValue(key, name)        # 删某个键下的一个值
```

`AppCompatFlags` 这类残留是**值**不是键。用删键的方法会报"键不存在"，然后整批中止——之前就踩过这个坑，表现是"0 清掉，4 项没动"。

### 3.6 AI：手动触发 + 上下文完整

**决策**：

1. **只在点按钮时联网**，默认 `ai.enabled=false`
2. **发完整已装软件列表**（167 个名字），不截断
3. **路径里的用户名替换成 `%USER%`**
4. **结果按 exe 路径缓存**，不按 PID

**为什么第 2 条很重要**：早期为了省钱只发前 50 个软件名，结果 AI 把"没在列表里"的软件全判成残留。167 个名字约 2223 token，一次几分钱，但误判要用户一条条核对——省这点钱不值。

**为什么不按 PID 缓存**：PID 每次重启都变，而且同一个程序开多个实例有多个 PID。exe 路径才是稳定标识。

### 3.7 一键清理类功能的尺度

这一类功能最容易变成"替用户做主"，所以设了几条硬规矩：

| 规矩 | 原因 |
|---|---|
| **只扫规则里写死的类别**，不自由发挥 | 用户能预料它会动什么 |
| **每类写清「删了会怎样」** | 删之前就知道后果 |
| **默认只勾 safe 的** | caution 的（系统日志）要用户主动勾 |
| **被占用的跳过，不强删** | 卡住或报错都比强删好 |
| **按类别勾，不逐条列** | 十几万项列表没法看 |

**空闲进程清理的三条判据**：开了多久 / 在不在前台 / CPU。这三条合起来才是"忘了关"的特征——单看任何一条都会误判：

- 只看年龄 → 输入法、驱动服务全中
- 只看 CPU → 后台更新进程也低
- 只看前台 → 你刚切走的程序

**额外排除四层**：

1. 系统进程名单
2. 会话 ID（服务在 0，查不到是 -1）
3. 桌面 shell（`explorer.exe` 动了就没桌面）
4. **父进程还活着**（微信拉起的 9 个插件属于微信，不是忘了关）

第 4 条是后来加的，因为前三条过滤完还剩 13 个微信插件进程。

### 3.8 配置必须容错

**决策**：每个字段独立校验，坏了退回默认 + 记一条 warning。

```python
class _Coercer:
    def boolean(self, data, key, default):
        ...
        self.warnings.append(f"设置项「{key}」写得不对，已经用默认值")
        return default
```

**为什么不用 `json.load` 一把梭**：用户手改配置时少个逗号就整个文件报废，然后所有设置回到默认——但用户不知道，以为设置生效了。

现在的做法是：坏的那个字段用默认值，其他字段照常生效，启动时告诉你哪项有问题。

## 四、数据结构

### 4.1 判定结果

```python
@dataclass
class Verdict:
    effect: str      # 这是什么
    impact: str      # 删了会怎样
    risk: str        # safe / caution / forbidden / unlisted
    source: str      # builtin / user / ""
```

`effect` 和 `impact` 分开是刻意的：一个回答"是什么"，一个回答"后果"。合成一句会两边都说不清。

### 4.2 操作报告

```python
@dataclass
class ItemResult:
    human_path: str
    ok: bool
    mode: Mode       # RECYCLE / PERMANENT
    error: str | None
```

成功和失败用同一个结构，界面直接遍历——不需要分两个列表再合并。

### 4.3 进程项

```python
@dataclass(frozen=True)
class ProcessItem:
    pid: int
    name: str
    ...
    ppid: int = 0          # 父进程，判断"是不是被人拉起来的"
    create_time: float = 0  # 启动时刻，算"开了多久"
    session: int = -1       # 会话 ID，区分服务和用户程序
```

`frozen=True` 是为了防止界面层意外修改。要改就重建一个。

## 五、错误处理原则

### 5.1 单条失败不影响整批

遍历里每个元素 `try/except`，失败的记下来继续。

```python
for item in items:
    try:
        ...
    except OSError:
        continue
```

**为什么**：一个被占用的文件不该让整批删除中止。

### 5.2 异常钩子只弹一次

```python
state = {"shown": False}
def hook(exc_type, exc_value, exc_tb):
    ...写日志...
    if state["shown"]:
        return
    state["shown"] = True
    QMessageBox.critical(...)
```

**为什么**：如果异常在事件循环里反复触发，弹窗会瞬间堆满屏幕。

### 5.3 备份失败不阻断删除

注册表值清理时，如果 `reg export` 失败，仍然继续删除——但会告诉用户"这一项没备份成"。

**理由**：备份是保险，不是前置条件。因为保险买不到就不办事，是本末倒置。

## 六、打包注意事项

| 项 | 说明 |
|---|---|
| `uac_admin=True` | 默认要管理员，写进 exe 清单 |
| 剔除 Qt 组件 | 省 20+ MB，但 `imageformats\qico.dll` **不能剔** |
| `datas` 相对路径 | 相对当前工作目录，`build.py` 用 `cwd=ROOT` 钉死 |
| `--noupx` | UPX 会拖慢解压 + 杀软误报 |
| 禁用 QtNetwork 等 | AI 客户端用 stdlib `urllib`，不需要 Qt 的网络栈 |

**剔组件时栽过的坑**：把 `imageformats\` 整个删了，导致 `QIcon` 加载 `.ico` 失败。而 `QIcon` 加载失败**不抛异常**，只是变成空图标——窗口标题栏悄悄退回默认图标，完全没有报错线索。

## 七、测试策略

### 7.1 用真实类型，不用 Mock

```python
# 反例：FakeItem 只有几个属性，隐藏了三处生产环境崩溃
item = FakeItem(path="x")

# 正例：用真实的 DeleteItem
item = DeleteItem(path="x", is_dir=False, size=0, ...)
```

早期用 Mock 对象图省事，结果上线后崩了三次——Mock 里没有的属性，真实类型上有默认值的差异暴露不出来。

### 7.2 测试自己造环境

所有涉及文件系统的测试在 `tempfile.mkdtemp()` 里跑，不碰真实目录。

涉及注册表的测试在 `HKCU\SOFTWARE\_dch_*` 下建临时键，跑完删除。

### 7.3 断言要断言行为，不是断言实现

```python
# 弱：只检查返回值不是 None
self.assertIsNotNone(result)

# 强：检查具体内容和类型
self.assertEqual(kill_args[0][0].__class__, int)   # 第一个参数必须是 pid
```

第二条是 `kill_process(obj)` 崩溃后加的——它检查的是**参数类型**，不是"跑没跑通"。
